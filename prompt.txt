# Project: Per-User, Per-Hour Active Directory Behavioral Baseline and Risk Scoring

You are a senior cybersecurity data scientist, Windows security-log analyst, and machine-learning engineer.

I have approximately 10 days of Windows Active Directory telemetry consisting primarily of:

* Windows Security Event Logs
* Sysmon Event Logs

The first 7 days are guaranteed to contain ONLY normal/benign activity.

Days 8–10 will be used as the testing period. These days may contain anomalous or malicious activity.

The goal is to build a behavioral baseline for every user and every hour of the day and then calculate a risk/anomaly score for every 10-minute test window.

The entire initial implementation should be developed in a **Jupyter Notebook**, with the notebook organized into clearly separated sections.

---

# 1. Core Objective

Build a behavioral profiling system with this structure:

```text
User
 └── Hour of Day
      └── 10-minute behavioral windows
           └── Feature vector
```

The baseline must be:

```text
USER-SPECIFIC + HOUR-SPECIFIC
```

It must NOT depend on the day of the week.

For example:

```text
Alice + Hour 09
```

should represent Alice's general normal behavior during 09:00–10:00 across all training days.

Monday 09:00, Tuesday 09:00, Wednesday 09:00, etc. all contribute to the same:

```text
Alice + 09:00–10:00
```

baseline.

---

# 2. Training and Testing Period

The dataset contains 10 days.

Use:

```text
Days 1–7 = Training / Baseline
Days 8–10 = Testing
```

The first 7 days are known to contain only normal activity.

Do NOT use Days 8–10 to construct the initial baseline.

Avoid all forms of data leakage.

# 3. 10-Minute Windowing

Divide the entire timeline into fixed 10-minute windows.

For every user, every hour contains exactly six windows:

```text
09:00–09:10
09:10–09:20
09:20–09:30
09:30–09:40
09:40–09:50
09:50–10:00
```

For 7 training days:

```text
6 windows/hour/day × 7 days = 42 observations per user-hour
```

Therefore:

```text
User Alice + Hour 09

Day 1 → 6 observations
Day 2 → 6 observations
Day 3 → 6 observations
Day 4 → 6 observations
Day 5 → 6 observations
Day 6 → 6 observations
Day 7 → 6 observations

Total = 42 ten-minute observations
```

---

# 4. IMPORTANT: Do Not Remove Empty Windows

Every user must have all 24 hours represented.

Every hour must contain all six 10-minute windows.

If a user has no events in a 10-minute window:

```text
09:10–09:20 → 0 events
```

DO NOT remove this window.

Instead create a feature vector containing zeros/default values.

For example:

```text
process_count = 0
network_count = 0
failed_login_count = 0
dns_count = 0
unique_process_count = 0
...
```

Similarly, if a user has no activity during an entire hour, that hour must still exist in the dataset with six zero/default feature vectors.

Do NOT exclude inactive hours from the baseline.

This is an intentional design decision because inactivity itself is part of the user's behavioral pattern.

# 6. User Identification

The primary user-identification source will be Windows Security Event ID 4624.

Use fields such as:

* TargetUserName
* TargetDomainName
* SubjectUserName
* SubjectDomainName
* LogonType
* LogonId
* TargetLogonId
* IpAddress

First, extract all Security Event 4624 events and create a mapping of **Username + LogonId + Computer + Timestamp**. Then map Sysmon Event 1 to the corresponding 4624 using **LogonId, Computer, and time correlation**. Once Event 1 is mapped, use its **ProcessGuid** to associate all related Sysmon events with that user. For remaining Security events, identify the user using event-specific fields such as **SubjectUserName, TargetUserName, UserName, LogonId, etc.** Finally, create one unified user-attributed event dataset, which will be divided into **10-minute windows** for feature extraction and baseline creation.

# 10. Behavioral Features Beyond Simple Counts

Do not rely only on event counts.

The baseline should also learn behavioral characteristics such as:

### Process identity

Which executables does the user normally run?

### Parent-child relationships

Which process relationships are normal?

For example:

```text
outlook.exe → chrome.exe
explorer.exe → powershell.exe
```

### Network destinations

Which IPs/domains/ports does the user normally communicate with?

### Authentication sources

From which workstations/IPs does the user normally authenticate?

### Rare events

Events that are extremely uncommon during the 7-day baseline should receive higher anomaly weight.

### Novel behavior

A process, destination, parent-child relationship, or authentication source never observed during training should be treated as potentially anomalous.

# 13. Risk Score

The final output for every 10-minute testing window should be a continuous score.

Example:

```text
0.00 → completely consistent with baseline
1.00 → highly anomalous
```

The score should represent behavioral deviation/risk.

Do NOT automatically call:

```text
risk = 0.95
```

"95% probability of maliciousness."

Unless a properly calibrated probabilistic model is developed and validated.

Instead clearly distinguish:

```text
ANOMALY SCORE
```

from:

```text
MALICIOUSNESS PROBABILITY
```

Initially the preferred output is:

```text
risk_score
anomaly_score
risk_level
```

For example:

```text
User: alice
Date: Day 8
Window: 09:10–09:20

Anomaly Score: 0.91
Risk Level: HIGH
```

# 14. Explainability

For every high-risk window, identify why the score is high.

Example:

```text
User: alice
Hour: 09
Window: 09:10–09:20

Risk Score: 0.91
Risk Level: HIGH

Reasons:

1. Process creation count is significantly above Alice's normal 09:00 baseline.
2. powershell.exe was not observed during the training baseline.
3. Destination IP X.X.X.X is new for this user.
4. Failed authentication count is significantly higher than normal.
5. A new process-parent relationship was observed.
```

The system should rank the strongest contributing factors.

---

# 15. Important Security Principle

An anomaly is NOT automatically malicious.

The system should answer:

> "How different is this activity from the user's normal behavior?"

It should NOT claim:

> "This activity is definitely malicious."

unless there is additional detection/correlation evidence.

Therefore use terminology such as:

```text
Normal
Low Risk
Medium Risk
High Risk
Critical Risk
```

rather than directly:

```text
Benign
Malicious
```

unless ground-truth labels are available.

# 20. Avoiding False Positives

The system should consider that unusual does not necessarily mean malicious.

Examples:

```text
User works overtime
User changes workstation
User installs approved software
User performs administrative activity
User connects to a new legitimate server
```

The baseline should therefore use robust statistics and behavioral context.

Avoid setting arbitrary thresholds without analyzing the training distribution.
